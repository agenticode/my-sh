MemorY

From M to Y of memory,one tool for all of it

A read-only open source tool that reads the memory error records of a server and draws where in a DIMM a fault sits and what shape it has.

GitHub agenticode/my Quick start in development

About

It only reads records

MemorY reads the memory error records a Linux server has already written. It does not offline pages, run repairs or reset counters.

What it reads goes into one ledger, keyed by the serial number of each DIMM. The history stays over reboots and follows a DIMM that moves to another slot.

Inputs rasdaemon DB kernel log EDAC sysfs SMBIOS BMC SEL Redfish nvidia-smi CXL mcelog FMFM JSON

Problem

Memory error logs are still read by hand

  1. Each source writes its own log format.
  2. Addresses have to be decoded into device, bank, row and column by hand.
  3. Counters start again from zero after a reboot.
  4. Whether the DIMM or the slot is at fault comes down to a guess.
  5. Figures for a report are drawn by hand.

Figures

The records as figures

Each figure answers one question. The screens below are the output of MemorY for lab captures in testdata/real of its repository. tools/captures.mjs ran each command in a terminal and took the screen as printed. Where a figure is cropped, it leaves out whole lines.

The first three figures show an aarch64 guest with six DIMMs. It was booted three times, a day apart, and firmware error records put 35 corrected errors (CE) and 1 uncorrected error (UE) into it. Four DIMMs got one fault each: a single cell, a row, a column and a bank. Two DIMMs got none. The next two figures show two guests whose boots kept stopping on fatal errors.

Testing

Tested on records that real kernels wrote

Memory errors at known places were injected into a Fedora VM on a lab server (kernel 7.3.0) and into QEMU guests inside it, and the records that the kernel and rasdaemon wrote were copied as they were. There are 17 captures, from kernels 7.3.0 and 6.19.10 and rasdaemon 0.8.0 and 1.0.0. They hold machine checks of x86_64 guests, errors of a CXL memory device, page offlining, firmware error records of aarch64 guests, and boots that stopped on a fatal error.

The figures above read three of them.

6.19.10-ghes-multi
An aarch64 guest with six DIMMs, booted three times a day apart. Four DIMMs got 36 firmware error records (35 CE, 1 UE).
6.19.10-bert-loop
An x86 guest, booted three times. At each reset QEMU wrote a hand-made BERT region, so at every boot the guest read that the boot before had ended in a fatal error in the same cell of DIMM 0 (row 0x1a2f, column 0x238). The guest was restarted with a reboot command.
6.19.10-ghes-loop-spread
An aarch64 guest with six DIMMs. In each of three boots one fatal firmware error record went to another DIMM (CPU0_A1, CPU0_C1, CPU0_E1). Each time the kernel stopped with a panic.

Reading the captures turned up 18 defects. They are fixed, and validation-lab.md describes each. Two of them:

  1. dmidecode 3.7 writes the size as 16 GiB. MemorY could not read that form and found none of the installed DIMMs.
  2. One panic of the aarch64 guest was saved in EFI variables as 16 parts. The parts were written over 3 seconds, so systemd-pstore put them into three directories. MemorY read them as three dumps and counted one panic as three boots, and 5 boots showed as 15. Now the parts that follow on from Part 1 are read as one dump.

The lab has no real memory controller, EINJ, BMC or GPU. Results from five running Linux hosts are in validation.md. All five are virtual machines, so none of them has an EDAC memory controller.

Start

Quick start in development

MemorY is one binary. Run it with no arguments:

$ my

There is no release yet. Build it from source with Go 1.26 or later.

$ git clone https://github.com/agenticode/my
$ cd my
$ make build    # bin/my

Without a server, try it on a lab capture of the repository. With --root set to a capture directory it reads the files of that host. Under a Korean locale it prints in Korean.
